# UX probe

The UX probe is a black-box reviewer. It runs as its own T3 Code thread whose working folder is the
probe folder, outside every repo. It reaches the product only through T3 Code's browser preview
tools (`mcp__t3-code__preview_*`, `mcp__t3-code__t3_preview_*`) on the local stack.

It is blind on purpose. It judges what a user meets: bugs, unclear copy, dead ends, missing
feedback. Knowledge of the code would bias it toward what the code intends.

## Isolation

| Layer | What it stops |
| --- | --- |
| A folder outside every repo | The thread starts with no code, no diffs and no project instructions in reach. `probe-init` refuses a folder inside a git work tree. |
| Permission denies by path | `Read` and `Edit` of each denied code folder, `~/.t3/worktrees`, `~/.claude/projects`, `~/.claude/plans` and `~/.codex/sessions`. A `Read` deny also covers Grep and Glob. |
| Permission denies by tool | `Bash`, `WebFetch`, `WebSearch`, and the T3 thread, project, worktree, environment, task and delegation tools. |
| The sandbox | `sandbox.filesystem.denyRead` repeats the denied paths as a backstop for Bash subprocesses only, not for the Read tool or MCP servers. `allowUnsandboxedCommands: false` ignores the unsandboxed retry. |

Deny rules beat allow rules and `--allowedTools` in every permission mode.

The isolation covers only the folders you pass with `--deny` and the four defaults, not every repo
on the machine. `probe-init` accepts a folder that contains a repo you did not deny. Pass `--deny`
for every code folder. Consider `~/.t3/userdata` too: it is T3 Code's own state, and a guess is
that it holds thread history.

## Limits

Other MCP servers the user has configured, a GitHub server for example, stay reachable unless you
pass them as `--deny-tool mcp__<server>`. The user's own settings still merge into the probe's:
arrays are joined, and a project file cannot remove the user's `excludedCommands` or network
allowances. That is why `Bash` is denied outright.

The localhost rule and "read nothing outside this folder" are instructions in `CLAUDE.md`. Nothing
enforces them, and a preview tool could open a `file://` URL.

## Folder layout

| Path | Holds |
| --- | --- |
| `CLAUDE.md` | A copy of `probe/CLAUDE.template.md`: the probe's instructions. |
| `brief.md` | This release's brief: the base URL and what changed, in user terms. |
| `briefs/` | Past briefs. |
| `journal.md` | One entry per run, newest first. |
| `candidates.md` | What the probe found, newest run last. |
| `verdicts.md` | Triage of the candidates. The probe reads it and never edits it. |
| `accounts.md` | The standing `qa-probe-` organization and its accounts. |
| `last-ref` | The git ref the last probed release ended at. |
| `screenshots/` | One screenshot per candidate. |
| `.claude/settings.json` | The deny rules and sandbox keys, regenerated by every `probe-init` run. |

`probe-init` never overwrites the files that hold the probe's history.

## Setup

```
probe-init <folder> --deny <each code folder> [--deny-tool mcp__<server>]
```

Then create a T3 Code project for the folder and launch the probe thread there. Re-run `probe-init`
when a code folder or an MCP server changes.

Put the probe folder in the product repo's Repo facts (`CLAUDE.md`). Optionally add it to that
repo's `permissions.additionalDirectories`, so writing the brief does not ask.

## Local stack and accounts

The probe visits only `localhost` or `127.0.0.1` and never starts or stops a server. It signs up one
standing organization named `qa-probe-<short word>` with accounts at `qa-probe-<role>@example.test`
and keeps their passwords in `accounts.md`. This is local test data only. It never enters real
personal or payment data, and it reports BLOCKED when sign-up needs an inbox or a payment.

## In a release

The `orchestrate` release playbook runs the probe after the release is proven:

1. `release-brief` writes `brief.md` from `last-ref` to the release's `HEAD`, in user terms only.
2. The playbook launches the probe thread in the probe's T3 Code project and waits for its
   `PROBE DONE` or `PROBE BLOCKED` line. BLOCKED skips triage and comes to you as an action.
3. Triage gives each new candidate one verdict, judged against the code: `confirmed`,
   `by design`, `duplicate` or `not reproducible`.
4. Confirmed candidates become slices you approve before the release PR.
5. Verdicts go back to `verdicts.md` in user terms, checked by `brief-lint`.
6. `last-ref` moves to the release's `HEAD`, so the next brief starts there.

The steps are in `skills/orchestrate/references/ux-probe.md`.
