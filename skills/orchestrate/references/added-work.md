# When the user adds work mid-run

Added work joins the run; it never becomes a side job in the main session.

1. **Check it against the plan file.** Work that fits the approved decisions is a new unit. Work
   that changes one is written into the plan file as a question, with options and your
   recommendation, and asked in the same exchange; only the units it touches park until it is
   answered. The rest of the run keeps going.
2. **Brief it on what the run already knows.** The brief builds on the run's `common.md` (in a run
   without a folder, the shared part of the briefs already written): the repo's knowledge, its
   standing rules, the skills to use. Never re-research what the plan file or `orchestrator.md`
   already holds.
3. **Add it to the unit table and spawn it** with a named model, under the same cap and the same
   sequencing rules as every other unit.

Never code it in the main session, however small: a one-line change is still a unit.
